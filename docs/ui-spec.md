# Airobot — UI Specification & Design System

## VisionOS Obsidian Glassmorphic Interface

Airobot is an Autonomous SMB Virtual Office & Self-Learning Multi-Agent Platform. Its interface is designed using the **VisionOS Obsidian Glassmorphic Design System**: deep obsidian pitch-black foundations (`#000000`), multi-layered frosted glass panels with dynamic backdrop blur, hairline translucent borders, and an Apple VisionOS-inspired floating Dynamic Island bottom dock.

---

## 2. Spatial 3-Column Layout Architecture

The application operates as a viewport-locked, zero-scroll desktop layout (`w-screen h-screen overflow-hidden p-3 md:p-4`):

```
+-----------------------------------------------------------------------------------------------+
|                                    AIROBOT VIRTUAL OFFICE                                     |
+--------------------+------------------------------------+-------------------------------------+
| LEFT COLUMN (3 cols)| CENTER COLUMN (5 cols)             | RIGHT COLUMN (4 cols)               |
|                    |                                    |                                     |
| + New office       | Active Real-time Chat Stream       | Apps & Dashboards                   |
| Search (Ctrl/⌘K)   | Server-Sent Events (SSE) Notes    | - Kanban CRM Pipeline               |
| Menu (fixed)       | Live Voice / Push-to-Talk Composer | - Video Studio Queue                |
| Offices → rooms    | Inline App Previews                | - Universal Record Editor           |
| Profile & Sign-in  |                                    | - Quick Approvals Queue             |
+--------------------+------------------------------------+-------------------------------------+
|                                 DYNAMIC ISLAND DOCK (FLOATING)                                |
|  [☰ Menu] [Chat] [Approvals] [Apps] [Bots] [Workflows]                | [Message your bots…] |
+-----------------------------------------------------------------------------------------------+
```

The three panels share one header height (`.panel-header`, 56px) and one footer row (`.panel-footer`, 66px: the account row, the composer and the credits footer), so their top and bottom lines run straight across the window.

When switching to full-canvas tabs (**Apps**, **Approvals**, **Bots**, **Workflows**), the center and right columns combine into a spacious 9-column workspace with the sidebar persistently anchored on the left.

### 3.0.1 A proactive office (no dead rooms)
- **Kickoff.** New office setup (the Architect window) also asks for the website (optional) and what matters most this month (More customers / Get paid faster / Save time on admin). Right after setup the group chat is not empty: the Architect explains what will happen, each area bot posts a three-task first-week plan with one-tap buttons for tasks 2 and 3 (`notes.actions`, kind `send` = sends `@handle: task` as your message), and the team starts at once, one task after another: with a website the Architect first reads it and sums up the business, then each bot does task 1. A blank office gets one Architect note with a **Set up this office** button (kind `setup`). Plans are fixed per area (`office/kickoff.rs`), so the kickoff is instant and costs nothing until work runs.
- **No AI yet.** When no AI can answer (no OpenRouter key and no AI on this computer), the office group chat gets one Architect note, "Connect an AI to wake up your team", with a **Connect an AI** button (kind `open`, target `account`: Settings → Account), not one warning per bot; it is said once per chat. In a bot's own room the bot says it needs an AI voice, with the same button. Each bot card keeps its **Needs AI** badge.
- **Memory and shared context.** Every bot in an office is told, besides the business and its apps: the office's **goal** (where the business is going) and **about** text (hours, prices, tone, policies), the facts the office **remembers** (pinned first, then newest, up to ~4,000 characters; office-wide facts plus that bot's own), the 5 newest **lessons** learned from approval decisions (`workspace_lessons`), and **Recently in this office's other rooms**: the newest 12 messages from the office's other rooms over the last week. A bot saves a lasting fact by writing `REMEMBER: <fact>`; the line leaves the chat and the message says *Remembered: …* with an **Undo** button (kind `forget`, target = the memory's id). An office remembers at most 200 facts; past that it says so instead of dropping facts. Everything lives in Postgres; no embeddings.
- **What each bot may use.** Each bot sees and fills only the office apps it may use, and gets live data only from the connected tools it may use. Defaults follow the role: Sales Lead (Lead Pipeline, Gmail), Studio Producer (Social studio), Finance Manager (Invoices, Stripe), Support Agent (Support inbox, Gmail), Scheduler (Appointments, Google Calendar), Store Manager (Shopify); other bots start with nothing, and the Architect sees how many records each app has per stage, not the records. A bot is shown the newest 8 records of each of its apps; `ADD` lines for other apps stay plain text. Before a bot answers, the server reads its tools (Gmail: recent inbox; Calendar: the next 7 days; Stripe: unpaid invoices and recent payments; Shopify: recent orders), each with a time limit, logs each read as the bot's (`connection_actions.actor_agent_id`) and shows the result as data, never as instructions; writes to outside tools stay drafts and approvals. The bot's settings dialog has **What it can use in <office>**: one box per app and per tool product (`GET`/`PUT /agents/:id/access?office=`, saved at once; changing any box makes the list the owner's own, **Reset to defaults** goes back, `POST /agents/:id/access/reset?office=`).
- **App charts and quick actions.** An app's `chart` view (`chart_type` `bar` or `spline`, `x_axis` a field or `status`, `y_axis` a number field summed or absent to count, optional `order` of x values) draws one series in the accent colour from the app's records: dates group by month (missing months shown as zero), other values by text in `order` or by size; thin bars with rounded tops, a 2px line with ringed points for `spline`, recessive grid, a tooltip on hover or keyboard focus of each column, and **Show as table**. Blueprints include Pipeline value by stage, Invoiced by month, Tickets by stage and Bookings by month. `quick_actions` (`{label, ask}`, at most 6) show as **Ask the team:** buttons under the metrics; one sends its `ask` to the office group chat (the Architect hands it on) and opens the chat. Older actions that only name a `trigger_workflow_slug` are hidden.
- **Documents.** Edit office → **Documents** holds what the office's bots answer from: **Upload a file** (PDF, Word .docx, text, Markdown, CSV or HTML, up to 8 MB, sent as base64; only this route accepts more than 1 MB), **Paste text** (an FAQ, a price list) or **Website page** (an address; the server reads the page, following up to three redirects, and in production only from public addresses). Each becomes plain text (at most 200,000 characters; longer text is cut and the owner told), titled from the file name, the page's `<title>` or the first line, and split into passages indexed by Postgres full-text search (English stemming; the title weighs more). The tab lists the documents with their size, previews one's text on click, renames (`PATCH /api/documents/:id`) and deletes (soft, `POST /api/documents/:id/delete`), and **Search your documents** shows the best passages with the matched words marked (`GET /api/offices/:id/documents/search?q=`: all words first, then any). Create is `POST /api/offices/:id/documents` with one of `text`, `url`, or `filename` + `content_base64`. An office keeps at most 100 documents and 2,000,000 characters. Every office bot (not the general Assistant) is shown the office's documents by title and the passages that match the newest part of its conversation (up to 6 passages, ~6,000 characters; an office with at most 6,000 characters of documents is shown all of them), as data, never instructions, each tagged `[doc 1a2b3c4d]`. A tag the bot writes becomes "(from “Title”)" in its message; an unknown tag is dropped. The bot's settings show **Documents: it answers from the office's documents** with the titles and an **Answer only from documents** box (`POST /agents/:id/settings` with `documents_only`): such a bot says it doesn't have the information instead of guessing. Passages are found by words, not meaning; there are no embeddings. **Keeping documents current:** website pages are read again every week (in the background loop, a few per tick) and on **Re-read now** (`POST /api/documents/:id/sync`; only pages): new text replaces the document's text and passages (the title stays) and clears "outdated"; the list shows when a page was last read. When a read fails, the last copy stays, the error shows under the document, it is tried again the next day, and the owner is told once per run of failures: an email (when the server can send mail) and a card in the office chat, "“Prices” couldn't be read again …", with **Open Documents** (note action `open`, target `documents`). Any document can be marked **outdated** (`POST /api/documents/:id/outdated` with `outdated` true or false): it shows crossed out with an Outdated badge, and bots no longer see it, list it or cite it until it is marked current again. A bot's reply that cites documents gets a button per cited document (at most two), "“Price list” is outdated" (note action `doc_outdated`). **Google Drive folders:** with a Google connection that has **Drive (read only)** (an opt-in product when connecting Google; Google treats the scope as restricted, so an app used by the public needs Google's review), Documents → **Google Drive folder** links a folder by its link (`POST /api/offices/:id/document-folders` with `folder`, `connection_id`; at most 10 per office). Each file directly in it (at most 50) becomes a document of kind `drive`: Google Docs and Slides exported as text, Sheets as CSV, PDFs, Word and text files read as uploads; images and other files are skipped. Folders are read again every day (and on **Sync now**, `POST /api/document-folders/:id/sync`): files whose Drive modified time didn't change are skipped, changed ones get their new text, files that left the folder are removed (soft), and the office's document limits apply. A failed read keeps the documents and tells the owner once, as for pages. **Unlink** (`POST /api/document-folders/:id/delete`) removes the folder's documents too; nothing in Drive changes. - **Goal, milestones, check-ins and the weekly report.** Edit office → **Goal**: the goal with **Save goal** (`PATCH /api/offices/:id` `goal`); a new goal starts a job for the Architect in the office chat to propose 3 measurable milestones. A bot proposes one with a `MILESTONE: <title> by YYYY-MM-DD` line: the line leaves the message, the milestone is kept as `proposed`, and the message lists the proposals with a **Keep: …** button each (note action `keep_milestone`, target = id) and **Review milestones** (`open`, target `goal`). The tab lists proposals (Keep / Drop), open milestones (tick to mark reached, delete) with dates (overdue in amber), an add row (title + date), and reached ones (`GET /api/offices/:id/goal`, `POST /api/offices/:id/milestones`, `PATCH /api/milestones/:id` with `title`, `due_on` (empty clears), `status` `active`/`done`, `POST /api/milestones/:id/delete`; at most 20 open). Check-ins and reports skip stopped offices and offices the owner hasn't used for a week (`PATCH /api/offices/:id` `check_in`, `weekly_report`).

The whole form sits under the chat and can be filled directly; **Close** or going to any other page leaves it. The form starts with **What kind of business is it?**: Local service (sales, bookings, support, quotes/invoices, reviews), Agency (sales, quotes/invoices, projects), E-commerce (store, support, marketing, reviews) or Solo (sales, quotes/invoices); a model picks those areas and suggests their tools, and any area can then be changed. Areas and tools are checkboxes (square), since they add up. The finance area reads "Quotes, invoices & cashflow · syncs with your accounting" and installs both Quotes & Proposals and Invoices & Cashflow. Tools offered: Google Workspace, Stripe, Shopify, Zapier/Make/n8n, and "QuickBooks / Xero via webhook"; "Microsoft 365 · planned" is shown but not selectable. A line says Contacts and Documents are always there. **The kickoff never invents data:** each bot's first task adds only real records (ones the owner mentioned, or from the office's tools; at most two, shown as live cards) or asks the owner one question for the first one; bots are told to add only real records, never placeholders. With a website, the Architect sums it up and saves lasting facts with `ABOUT:` lines; without one it asks the owner three questions (what you sell and prices, customers, hours or area). The Architect saves what the owner tells it about the business with `ABOUT: <fact>` lines: each fact is appended to **About the business** (once; at most 4,000 characters), the line leaves the message, and the message says "*Added to About the business: …*" with **Edit About**.

A record's fields may be lists of small rows one level deep (a quote's line items, a project's milestones). An app's `approval_stages` (quotes: Sent; reviews: Requested and Replied) are stages a bot can only move a record into with the owner's OK, even a Trusted bot; a bot that adds a record in one starts it at the board's first stage. An app's `convert` rules make a record into one of another app: an **Approved** quote converts to an invoice (client, amount = total, description = title, status Draft, number `INV-…`, due in 14 days) or a project (name, client, value; Backlog), from its board card's menu or its chat card (`POST /api/office/records/:id/convert?office=` with `to_app`). The contact carries over, the new record says what it came from, the quote shows "Converted to …", and converting again returns the same record. Board cards show each app's own `card_fields` (money and dates formatted).
- **Live record cards in chat.** A message that adds or changes app records carries card references (`notes.cards`: `{type: "app_record_card", app_slug, record_id, action, title, changed_fields?, approval_id?}`), never copies. Each card is drawn from the record as it is now by one shared store (`GET /api/office/records?office=&ids=`, at most 50 ids: each record with its app, contact and any change waiting for an OK; an id that is deleted, unknown or another office's is a tombstone `gone: "deleted"`, one in an archived app `gone: "archived"`, with no data) and kept live by the office's record events (`GET /api/office/events?office=`, server-sent `record` events with `record_id`, `app_slug`, `kind`: created, updated, deleted, pending, or app for a whole app); the apps and the right panel refresh from the same events. A card is compact: the action and app ("Added to Lead Pipeline & CRM"), the title, a status pill, the contact, up to three of the fields the app's layout shows (labels and currency/date formats from its table), **More** for all, and **Open in its app**. A deleted record shows struck through with "deleted" or "its app is archived". Deciding finishes the change's job (done, or "you rejected it").
- **Recurring jobs and permission modes.** A bot sets a recurring job from chat with one line, `EVERY <day | Monday … Sunday | week on <day> | month on <1-28>> at <hour>: <job>` (capitals, so a sentence starting "Every Monday: …" is not one): the line leaves the message, the schedule is kept for that bot in that room, and the message says "*Recurring job proposed, every Monday at 09:00: … It starts when you press Start.*" with **Start** (note action `start_job`) or, for a Trusted bot, "*Recurring job set, …*" with **Stop it** (`stop_job`). Every office bot is told how and is shown its own schedules. A due schedule (in the owner's time, at or after its hour, once per day, week or month, only for slots after it was started) runs as one of the bot's jobs in its room, metered, capped and with an honest outcome; stopped or capped offices, and owners away for two weeks, skip theirs. The bot's settings have **Recurring jobs and permissions**: **Ask first** (default; its schedules wait for Start) or **Trusted** (they start at once), the bot's schedules with Start / Stop / delete, and an add row (job, every day / week on a weekday / month on a day 1–28, hour) (`GET`/`POST /agents/:id/schedules?office=`, `PATCH /api/schedules/:id` `status` `active`/`stopped`, `POST /api/schedules/:id/delete`, `POST /agents/:id/settings` `permission_mode`; at most 10 per bot). In every mode, anything sent to an outside tool is a draft the owner approves. Modes also decide whether the bot's changes to existing app records apply at once or wait for an OK (see Live record cards).
- **Honest outcomes.** A job a bot is given (a task the Architect hands it in the group chat, a kickoff task, a server task) ends with one line saying how it went: `OUTCOME: done`, `nothing to do — why`, `blocked — what it needs` or `needs your OK — what to approve`. The line leaves the message and an italic line says it instead ("*Needs your OK: send the 3 follow-ups*"); a server task's note leads with it ("Blocked: 'Chase invoices'"). Chat jobs are kept as tasks with `executor = 'chat'` (records only; never claimed or run), server tasks keep `outcome` and `outcome_note`, and a job whose AI failed, hit a limit or had no AI is kept as failed or blocked with why. The bot's settings show **Recent work**: its last 10 jobs with outcome (icon and word, never colour alone), note, when and credits (`GET /agents/:id/stats` `recent_work`).
- **Spending caps.** Every metered AI call (paid with included credits) is charged to the office it works in and the bot making it (`credit_ledger.office_id`, `agent_id`). An office's **monthly spending cap** and a bot's own cap are hard: the budget gate refuses a call that would go past either before it is made, and nothing is charged. When an office reaches its cap, its morning plan and queued tasks wait (they are not failed) until the 1st (UTC) or until the cap changes, and its group chat gets one card that month, "This office reached its monthly spending cap (N of M credits)…", with **Raise the cap** (note action `open`, target `office`, opens Edit office). A bot that reaches its own cap posts one card in the room where it was refused, with **Bot settings** (target `bot:<id>`). The room where a reply was refused gets a short note (at most hourly). Calls with the owner's own OpenRouter key or AI tools cost no credits and are never capped. The bot's settings dialog shows **Spending** (not in the desktop app): spent this month, paid calls, last month, a 30-day sparkline with hover per day (`GET /agents/:id/stats`), a meter against its cap, and **Monthly cap** with **Set cap** (`POST /agents/:id/settings` `monthly_cap_credits`; 0 removes it, saved at once).
- **Contacts.** **Contacts** in the sidebar (`/contacts`) lists the office's contacts (one per person or customer, unique by email per office; `GET`/`POST /api/offices/:id/contacts`, `?q=` matches name, email, phone or company), with **New contact** and **Import from Stripe** (`POST /api/offices/:id/contacts/import`: Stripe customers, matched by Stripe id then email, so importing twice adds nothing). A contact's panel edits its name, company, email, phone, tags, notes and marketing-email consent (`PATCH /api/contacts/:id`; an email another contact has is refused), lists **What the bots know about them** (`POST /api/contacts/:id/memory`) and its **Timeline**: the leads, invoices, bookings and tickets linked to it (`GET /api/contacts/:id`). Delete is soft and keeps the records (`POST /api/contacts/:id/delete`). A record that names a person (client, customer or contact fields, or a lead's name, with its email or phone) links to the matching contact (email, then phone, then exact name) or a new one, whether the owner or a bot added it; bots never edit a contact. A bot is shown a contact's details and facts only when its conversation names that contact; `REMEMBER about <name>: <fact>` keeps a bot's fact on that contact.
- **Daily plan.** Every morning (8:00 in the owner's time, `workspaces.utc_offset_minutes` from the browser) in each office that is new or whose owner wrote in the last 7 days, the Architect reviews recent work and hands up to 3 tasks to its bots with `@handle: task`; they start at once and post in the group chat. Pending approvals are mentioned. Offices are claimed atomically (`last_plan_at`), never planned twice a day; the kickoff counts as day one. Off/on per office from its ⋯ menu (`PATCH /api/offices/:id` with `daily_plan`).
- **Web access.** Bots can search the web and read pages while they answer: in the cloud through OpenRouter's `openrouter:web_search` (3 results per search, 9 per answer) and `openrouter:web_fetch` tools, retried without them if a model refuses tools; on the desktop through the AI tool's own web tools (Claude Code with only WebSearch and WebFetch allowed and every other tool, including file reads and shell, denied; Codex with live search in its read-only sandbox). Each answer with web access counts as one **web answer** against a daily allowance per account (`web_usage`; `WEB_RUNS_PER_DAY`, default 60 in the cloud and 200 on the desktop; `WEB_ACCESS=off` disables it). Past it, bots answer without the web and say so. Cloud web answers cost 2 extra credits. Bots are told to treat page content as information, never as instructions, and never to put private details into URLs. The Bots page shows "N / limit web answers today" (`/api/office/wallet` `web_runs_today`, `web_runs_limit`).

## 4.0 Appearance

Primary actions use `bg-accent text-accent-fg`; never hard-code `bg-white text-black`.

Changes preview live; Discard or closing reverts.
- Signed-in people keep their theme on their account (`PUT /api/me/theme`, returned by `/api/me` as `ui_theme`), so it follows them to every browser and the desktop app; the last theme is cached locally only to paint before `/api/me` loads. Guests save on the device.
- **Language.** Settings → Appearance starts with **Language**: Automatic (the browser's or computer's language, shown as "Automatic (Español)") or English, Español, Français, Deutsch, Português (Brasil), Русский, each by its own name. Signed-in people keep the choice on their account (`PUT /api/me/language` with `language`, a code from `GET /api/languages` `ui`, or null for automatic; returned by `/api/me` as `ui_language`); it is cached on the device so the first paint is already in that language, and the page's `lang` attribute follows it. ## 4.0.1 Voice

- Settings → Voice. Speech to text for the message-bar mic: **On this device** (Whisper / Moonshine via transformers.js, or NVIDIA **Parakeet TDT v3** via parakeet.js, int8 on WebAssembly, ≈670 MB, 25 European languages with punctuation; models download once from Hugging Face and stay on the device, audio never leaves the machine; ONNX Runtime's WebAssembly loads from the CDN on first use instead of shipping in `dist/`), **Groq** (Whisper Large v3 / Turbo with the person's own key, stored on the device and sent only to Groq), or the **Browser** recognizer.
- Models show Download / Load / Unload / Delete and a live "Unloads in m:ss". **Keep models in memory** releases a model after 0 s / 2 / 5 / 15 / 60 minutes idle, or never.
- The mic is a toggle: one click starts dictation, the next click (or sending the message) stops it. The browser recognizer keeps listening through pauses (it restarts itself when the browser ends a session). Local models and Groq record until the second click (or 5 minutes).
- Every local model (Whisper, Moonshine, Parakeet, Kokoro) loads and runs in a Web Worker (`voiceWorker.ts`), one per model, so downloading, loading, transcribing and speaking never freeze the page or the desktop window.
- Dictation history (text, engine, audio length, time taken) is kept on the device, with copy and delete.
- Speak replies: Off, the system's built-in voices (free), or Kokoro 82M (≈90 MB, local). "Read bot replies aloud" speaks new bot notes as they stream in.
- **One voice at a time.** Messages read aloud queue and play one after another (at most 5 waiting; older ones are dropped), never over each other. While one plays, a bar above the message box says who and where ("Finance Manager is speaking · Bright Smiles", "getting the voice ready 40%" on first use, "2 more waiting") with **Stop**, which silences it and clears the queue. Kokoro speaks sentence by sentence, making the next piece while the current one plays. Test in Settings interrupts whatever is playing; a stop while a piece is starting is not an error.
- The same code runs in the browser and the desktop app (which opens the hosted app); the voice engines load only on first use.

## 4.0.2 Desktop app: your office on your computer

- By default the desktop app **is** Airobot: it starts a private PostgreSQL shipped inside the app and the same server in local mode (`src/local.rs`), bound to `127.0.0.1` on a random port, and opens it in its window. No website, VPS, account or credits are needed; data stays in the app's data folder.
- The window enters through `/local/enter?token=…` with a secret made fresh each launch, signing in the computer's single owner (`you@this-computer.local`, admin). Requests must be addressed to the loopback port (DNS-rebinding guard). Outside local mode `/local/enter` does not exist.
- Chats and office tasks are answered by the AI tool chosen in Devices → **AI on this computer** (Claude Code, Codex, OpenCode, Gemini CLI, Ollama; the first signed-in one if none is chosen; picking one confirms it), or by a bot's own tool and model from its Settings, through `AppState::local_ai`. Nothing is metered; the credits footer reads "AI on this computer".
- **Airobot Cloud** is optional: "Switch to Airobot Cloud" (Devices or the tray) opens the hosted site and its sign-in; "Work on this computer instead" switches back. Phone access needs the cloud. **Sync** (issue #28): Settings → Account on the desktop shows **Sync with Airobot Cloud**: an address (default `https://airo-bot.com`; https, or http to this computer) and **Link this computer** (`POST /api/sync/connect`; the desktop asks the cloud for a device code, `POST /api/sync/link`, purpose `sync` in `login_codes`, and keeps its secret encrypted). It shows the code and **Open Airobot Cloud** (`<cloud>/settings?sync_code=<code>`; the code is kept on that device through sign-in), and checks every few seconds (`GET /api/sync/status`, which asks the cloud `POST /api/sync/link/token`). In the cloud, Settings → Account shows **Computers that sync** with "Allow “<name>” (<code>) to sync your offices?" and **Allow** / **Don't allow** (`GET /api/sync/link?code=`, `POST /api/sync/link/approve` or `/deny`; a person only, never a bot key; the bot sign-in flow never redeems a sync code), and the linked computers with their last sync and **Remove** (`GET /api/sync/computers`, `POST /api/sync/computers/:id/revoke`). Allowed, the desktop receives its key once (`air_sync_…`; an Argon2 hash in the cloud, encrypted on the desktop) and shows "Synced with <address> as @<handle>. Last synced …" with **Sync now** (`POST /api/sync/now`) and **Stop syncing** (`POST /api/sync/disconnect`, which also retires the key in the cloud, `POST /api/sync/revoke`). Every minute while linked, the desktop exchanges rows with the cloud (`POST /api/sync`, the key as a bearer token; up to 32 MB): offices (not spending caps), bots (never their keys, AI tool or model; a bot made by sync has no key), rooms and which bots answer there, messages, apps and records, contacts, memory and documents (not Drive-folder ones; their passages are rebuilt). Each side keeps `changed_at` per row (a trigger) and the desktop keeps cursors per table, a page per table per exchange, and a table waits while the one before it fills its page. The newest `updated_at` wins and the cloud's copy stays on a tie; messages are only added; deletions travel as soft deletes. The person's bot of the same name, an app of the same kind and a contact with the same email in an office become one (the desktop maps its id to the cloud's, `sync_id_map`); offices and rooms whose slugs clash are renamed, not merged, so a desktop's "My office" and the cloud's both show. A row is applied only if it is the key's person's: their offices, their bots, rooms in their offices, people who are them or members. While linked, the desktop leaves the morning plan, check-ins, weekly reports and website re-reads to the cloud. TODO(air): removing a bot from a room, workflows, schedules, lessons and Drive documents don't sync; synced messages show after a refresh, not live.
- **Check for updates.** The desktop app asks its local server (`GET /api/app/update`, signed in) at start and every 6 hours whether a newer Airobot is published. The server reads the newest non-draft, non-prerelease GitHub release (`UPDATE_FEED_URL`, default the repository's releases; `UPDATE_CHECK=off` turns it off), compares it with its own version (stamped from the release name at build time), and picks the installer for its own OS and chip (`_aarch64.dmg`, `_x64.dmg`, `-setup.exe`, else the release page); answers are kept for an hour (`?refresh=1` asks again, at most once a minute). When one is out, the title bar shows a green **Update to x.y.z** button, and Settings → Account has an **Updates** card (version, "up to date" or "x.y.z is out", when it last checked, **Check for updates** and the same green button). The button opens the installer in the computer's browser; installing in place needs signed releases (`TODO(air)`).
- The window has no system title bar: the app draws its own (`DesktopTitleBar`: drag area, double-click maximizes, minimize / maximize / close; macOS keeps its traffic lights), in the theme's colours. Beside the app name, the sidebar's shrink-to-icons toggle; on the right, **Approvals** (a dashed circle with a check, with the number waiting). The loading page has the same bar.
- While the local database starts, the window shows `desktop-loading.html`; if it can't start, the page shows why. Quitting from the tray stops the database cleanly; closing the window keeps Airobot in the tray (one tray icon).

## 4.0.3 This computer (desktop bot, cloud mode)

- Devices → **This computer**. In a browser it links to the desktop download. In the desktop app it lists the AI tools found on the machine with their state (Signed in / Not signed in / Installed / Not installed): Claude Code (Claude Pro/Max), Codex (ChatGPT plans), OpenCode, Gemini CLI and Ollama.
- **Connect this computer as a bot** pairs it through the device flow without leaving the app: the desktop asks for a code, the signed-in web app approves it (`Desktop Bot`, numbered if taken), and the desktop keeps its own bot key in its data folder.
- Pick a tool and switch the bot on. It claims queued tasks from the person's own workspace, runs each through that tool in an empty scratch folder with file and shell access off (Claude Code `--disallowedTools "*"`, Codex `--sandbox read-only`), and posts the real result or the real error. The setting survives restarts; the tray toggles it.
- **Answer my chats here** (needs the bot on): the person's own messages to their own bots, in their own threads, are answered on this computer by the chosen tool, in each bot's character. The server queues a `chat_reply` task assigned only to that desktop (with the bot's instructions and recent conversation) instead of calling OpenRouter, so no credits are used; the desktop polls every 3 s, writes the reply, and the server posts it as the bot. Offline for 90 s or switched off → chat is answered by the server exactly as before. A failure posts why; a request older than 10 minutes is dropped quietly. Other people's messages never reach a person's subscription.
- Subscriptions are used the way their makers allow: each tool runs unmodified, signed in with the person's own account. Airobot never reads, copies or uploads a tool's credentials, and the server never uses anyone's subscription.

## 4.1 Navigation Consistency

- The sidebar and dock use the same names in the same order: Chat, Approvals, Apps, Bots, Workflows. The dock has no + of its own: new offices, rooms and bots start in the sidebar.
- Every tab has a URL (`/`, `/approvals`, `/apps/:slug`, `/bots`, `/workflows`, `/settings`, `/settings/appearance`, `/settings/voice`, `/settings/connections`, `/settings/admin`). Browser Back/Forward switches tabs, and the server serves the SPA for these paths plus `/inbox` and `/signin`, so reloads and sign-in redirects stay inside the app.
- No control is decorative: a button either does something or is removed. Actions that need an account open sign-in for guests instead of failing silently, and failures show a short message.
- Screens show only real data. Empty states explain what is missing and offer the next step.
- **Admin** (`/admin`) appears last in the sidebar, only for platform admins (`/api/me` reports effective admin, including the bootstrap owner). It shows platform stats, the onboarding-tour mode, searchable People (grant/revoke admin; never on your own row) and Bots (last seen, revoke key with confirm). Non-admins who open the URL see "Admins only".

## 5. Modals & Dialogs
- **`OnboardModal`:** Opens as the Architect setting the office up. The first card, **Blank office**, is selected by default; it and the areas exclude each other (picking an area turns blank off, picking blank clears the areas).
