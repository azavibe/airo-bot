## 1. Product patterns: how business AI agent products ingest knowledge, cite it, keep it fresh, and scope it

### Takeaway
Every major product supports the same three ingestion paths: file upload, public URL/website crawl, and connector sync (Drive/SharePoint/help desk). They differ mainly in (a) scoping: per-agent, shared "brain", or many-to-many data stores; (b) freshness: manual re-sync, weekly re-crawl, or live sync; and (c) how much they expose about what was retrieved. Citations are now table stakes. Conflict and staleness handling is still immature: only Intercom and, per a competitor review, Chatbase ship explicit "contradictory content" detection, and Copilot Studio relies on a manual "official source" flag.

### Inferences
- Common feature set to match: upload (PDF/DOCX/PPTX/TXT/MD/HTML/CSV), website/sitemap crawl with URL-stem scoping and exclusions, Drive folder sync, an internal-only "snippet/FAQ" type, a scheduled re-sync with visible status and failure alerts, and per-answer source links.
- Scoping options seen: per-agent (Copilot Studio, Custom GPT), per-project (ChatGPT/Claude Projects, NotebookLM), one shared brain for all bots (Sintra), and many-to-many apps↔data stores (Gemini Enterprise). For Airobot, an office-level library with per-bot attachment (many-to-many) covers both the Sintra "shared brain" and the per-bot cases. The existing `private`/`unlisted`/`public` visibility can drive whether a source is citable to outside visitors. HubSpot's "private sources aren't cited but content may still appear" is a leak pattern to avoid.
- The Claude Projects / Relevance AI pattern of whole corpus in context when small and retrieval tool when large is the simplest UX: users never pick a mode.
- Exposing what the bot retrieved (Copilot Studio test pane, Claude's visible search tool call, Amazon Q per-document sync reports) directly answers the "can't see what the bot knows" complaint in section 2.

## 2. User sentiment: what users praise, complain about, and request

### Takeaway
The dominant complaint across products is silent retrieval failure: the bot ignores or "forgets" loaded documents, answers from general knowledge, or fabricates citations, and users can't see why. Next come sync and freshness problems (full re-crawls, failed syncs, outdated content) and opacity about how content was learned. Requests cluster around incremental/automatic sync, flagging outdated or contradictory content, strict "only from my docs" behavior with honest "I don't know", and visibility into retrieval. Ease of setup is the most common praise. Reddit could not be searched, so small-business forum sentiment is under-represented.

### Inferences
- The highest-value UX features for trust are: (1) every answer that used documents shows clickable sources (document + section/page) generated from retrieved chunk ids, not model-written URLs, which addresses fabricated citations; (2) a "what does this bot know" view listing attached sources, sync status, last-indexed time and chunk counts; (3) a per-bot "answer only from documents" toggle that makes the bot say "not in my documents" rather than guess; (4) a "test retrieval" panel showing the top chunks for a query (as in the Copilot Studio test pane).
- Freshness features worth shipping early because users ask for them by name: scheduled re-sync with per-source status, failure alerts (an office notification), "mark outdated" on a source from a chat answer, and keeping old versions (soft-delete fits the project rules).
- Contradiction detection is a differentiator today (Intercom, reportedly Chatbase). It could be a later bot task: compare chunks retrieved for the same question across documents with different dates. Mark as TODO.

## 3. Implementation inside one PostgreSQL database: FTS vs trigram vs pgvector, hybrid with RRF, chunking, embeddings, and the no-embeddings option

### Takeaway
For tens of thousands of chunks per workspace, built-in Postgres full-text search (a generated `tsvector` column with a GIN index, `websearch_to_tsquery`, and `ts_rank_cd`) plus `pg_trgm` for typo-tolerant title matching works on the stock `postgres:16` image Airobot already uses, needs no API key, and is "good enough" for the lexical side by practitioner accounts. pgvector adds semantic recall but requires switching to the `pgvector/pgvector` image (official Postgres images don't bundle it), embedding calls with the user's key or a local model, and dimension caps of 2,000 for indexed `vector`. The well-trodden hybrid recipe is to run both queries separately and fuse with Reciprocal Rank Fusion (k ≈ 60) in one SQL statement. At these volumes, an exact (unindexed) vector scan filtered by workspace is reasonable. For very small corpora (under ~200K tokens), skipping retrieval and putting everything in context is officially recommended by Anthropic.

### Cited Findings

**Postgres full-text search and trigram**
- `websearch_to_tsquery` accepts web-style syntax (quoted phrases, `-` exclusion, `OR`) and is recommended (along with `plainto_tsquery`/`phraseto_tsquery`) for untrusted user input. `ts_rank` ranks by lexeme frequency, while `ts_rank_cd` is cover-density ranking that rewards proximity. Weights can boost titles over bodies, and normalization flags divide by document length. Stored generated `tsvector` columns must pin an explicit text search config because generated expressions must be immutable. GIN is the usual index. — [PostgreSQL docs: textsearch controls (v10 mirror)](https://www.postgresql.org/docs/10/textsearch-controls.html); [Tessl postgres text search reference](https://tessl.io/registry/alonso-skills/postgres/files/references/20-text-search.md); [OneUptime: PostgreSQL FTS (2026-01)](https://oneuptime.com/blog/post/2026-01-21-postgresql-full-text-search/view)
- `pg_trgm` gives `similarity()`/`word_similarity()` and `%` for typo tolerance and partial matches, indexed with `gin_trgm_ops`. FTS works on stemmed lexemes and cannot do substring matching. — [Postgres is Enough, ch. 6](https://cloudstreet-dev.github.io/Postgres-is-Enough/ch06-full-text-search.html); [ParadeDB: FTS in PostgreSQL](https://www.paradedb.com/learn/search-in-postgresql/full-text-search) (snippet)
- Criticisms of `ts_rank` (vendor sources): it "uses an ad-hoc scoring function" lacking BM25's properties, and one vendor cites a Stack Overflow report of queries degrading from under 1 s to 25–30 s on 800,000 rows when sorting by `ts_rank`. pgEdge notes Postgres retrieves all matching rows and then re-ranks them. — [Tiger Data: pg_textsearch BM25](https://tigerdata.com/blog/pg-textsearch-bm25-full-text-search-postgres) (snippet); [ParadeDB: BM25 in PostgreSQL](https://www.paradedb.com/learn/search-in-postgresql/bm25) (snippet); [pgEdge vchord-bm25 comparison](https://docs.pgedge.com/vchord-bm25/v0-3-0/comparison-to-other-solution-in-postgres/)
- BM25 extensions exist: ParadeDB `pg_search` (built on Tantivy, AGPL-licensed, with a vendor claim of 20x faster than tsquery/ts_rank over 1M rows) and Tiger Data `pg_textsearch` (BM25, v1.0 announced on postgresql.org; scores are negative, lower is better; in preview on Azure HorizonDB). — [ParadeDB: introducing pg_search](https://paradedb.com/blog/introducing_search) (snippet); [PostgreSQL news: pg_textsearch v1.0](https://www.postgresql.org/about/news/pg_textsearch-v10-3264); [Azure HorizonDB FTS](https://learn.microsoft.com/en-us/azure/horizondb/ai/full-text-search); [awesome-search: ParadeDB](https://frutik.github.io/awesome-search/Tools/ParadeDB)

**pgvector: facts, availability, operations**
- Latest pgvector is v0.8.7. The Docker image `pgvector/pgvector:pg<major>-trixie|bookworm` "adds pgvector to the official Postgres image" for Postgres 15–19. For parallel HNSW builds, `--shm-size` must be at least `maintenance_work_mem`. — [pgvector README](https://github.com/pgvector/pgvector)
- Index dimension caps: `vector` 2,000 (type allows 16,000), `halfvec` 4,000, `bit` 64,000, `sparsevec` 1,000 non-zeros (HNSW only). — [pgvector README](https://github.com/pgvector/pgvector)
- HNSW has better speed/recall than IVFFlat but slower builds and more memory, and it can be created on an empty table (no training). IVFFlat builds faster with less memory but must be created after data exists. Filters apply after the ANN scan, so results can fall short. Since 0.8, `SET hnsw.iterative_scan = strict_order` (or `relaxed_order`) keeps scanning until enough rows match. Exact search is the default with "perfect recall", and "if the table is small, a table scan may be faster". The README recommends pairing with Postgres FTS for hybrid search via RRF or a cross-encoder. — [pgvector README](https://github.com/pgvector/pgvector)
- Airobot's `docker-compose.yml` uses `image: postgres:16` (the official image without pgvector). — local file `/home/user/airo-bot/docker-compose.yml` line 13; the existing group-chat module states "No embeddings or search" — `/home/user/airo-bot/src/office/group.rs` line 4
- Managed availability: AWS RDS PostgreSQL 15.2+ (all regions). Azure Database for PostgreSQL Flexible Server. Google Cloud SQL for PostgreSQL 12+ (pgvector 0.6.0 per a 2024 announcement; current version not confirmed). Neon on every plan (lists 0.8.0). Supabase via dashboard or `create extension vector`. — [Discourse Meta: pgvector on RDS](https://meta.discourse.org/t/is-there-a-recommended-way-to-get-pgvector-on-rds/288641); [Encore: pgvector on RDS (2026-11)](https://encore.dev/articles/pgvector-aws-rds); [Azure Tech Community](https://techcommunity.microsoft.com/blog/azuredevcommunityblog/easily-deploy-a-pgvector-enabled-postgresql-server-to-azure/4107871); [Google Cloud: pgvector 0.7.0 in Cloud SQL](https://cloud.google.com/blog/products/databases/pgvector-0-7-0-support-in-cloud-sql-for-postgresql); [Cloud SQL: work with vectors](https://docs.cloud.google.com/sql/docs/postgres/work-with-vectors); [Neon pgvector docs](https://neon.com/docs/extensions/pgvector); [Supabase pgvector docs](https://supabase.com/docs/guides/database/extensions/pgvector) (snippet)
- Scale guidance: "Default Postgres + pgvector works great for initial RAG development and small corpora". Tuning, quantization and extensions become necessary past a few million high-dimensional vectors. Reasons to leave Postgres are sub-20 ms p99 under heavy concurrency, billions of vectors, or frequent re-embedding causing MVCC bloat. — [ClickHouse engineering: scale vector search in Postgres](https://clickhouse.com/resources/engineering/scale-vector-search-postgres) (competitor-authored)

**Hybrid search and RRF in Postgres**
- Supabase's documented hybrid search runs tsvector FTS and pgvector semantic search separately and fuses them with RRF. Its function takes per-method weights (`full_text_weight`, `semantic_weight`) and an `rrf_k` smoothing constant. The snippet gives the default as 50, and the guide uses an HNSW index. — [Supabase: hybrid search](https://supabase.com/docs/guides/ai/hybrid-search) (snippet; page blocked)
- Other examples use score = Σ 1/(k + rank) with k = 60, including Google AlloyDB's SQL example. — [AlloyDB: hybrid vector similarity search](https://docs.cloud.google.com/alloydb/docs/ai/run-hybrid-vector-similarity-search?authuser=0); [pgEdge pgvector hybrid search](https://docs.pgedge.com/pgvector/v0-8-1/hybrid-search)
- Practitioner view: tsvector+GIN is "good enough" for the lexical branch of most RAG, since "the dense branch carries the semantic signal and the lexical branch only needs to catch identifiers and rare tokens". RRF is "a robust default. No calibration needed." — [ClickHouse engineering](https://clickhouse.com/resources/engineering/scale-vector-search-postgres); [DEV: hybrid search in 100 lines, BM25 + pgvector with RRF](https://dev.to/gabrielanhaia/hybrid-search-in-100-lines-bm25-pgvector-with-rrf-merge-58cn); [Railway: hybrid search with pgvector](https://docs.railway.com/guides/hybrid-search-postgres-pgvector)
- Hacker News practitioners: one team runs hybrid dense + BM25 "since dense doesn't work well for technical words". Another says BM25 alone "gives you very relevant results if you can do some work during ingestion time with an LLM", and that hybrid works better "though not by that much". - An arXiv paper cites a Microsoft whitepaper calling hybrid search with reranking "table stakes" for RAG. — [arXiv 2609.36326 (PILLAR)](https://arxiv.org/pdf/2609.36326)

**Anthropic contextual retrieval and the "no RAG" threshold (Sep 2024, older)**
- "If your knowledge base is smaller than 200,000 tokens (about 500 pages of material), you can just include the entire knowledge base in the prompt", and prompt caching cuts latency by more than 2x and cost by up to 90%. — [Anthropic: Contextual Retrieval](https://www.anthropic.com/news/contextual-retrieval)
- Top-20 retrieval failure rate fell from 5.7% to 3.7% (−35%) with contextual embeddings, to 2.9% (−49%) when contextual BM25 was added, and to 1.9% (−67%) with reranking (retrieve 150, keep 20). Twenty chunks beat 5 and 10. The cost example uses 800-token chunks with 50–100 tokens of generated context per chunk, at $1.02 per million document tokens one-time. Gemini Text 004 and Voyage embeddings performed best, and Cohere was the reranker tested. — [Anthropic: Contextual Retrieval](https://www.anthropic.com/news/contextual-retrieval)
- Claude Code's creator said early versions used RAG with a local vector DB, but agentic search (grep/glob/read in a loop) "outperformed everything, by a lot". This is secondhand coverage of a May 2025 podcast. Counterpoints are token cost on large corpora, and one report has RAG beating agentic search on a large paper corpus. — [OfficeChai](https://officechai.com/ai/claude-researcher-explains-how-agentic-search-performed-better-than-rag-for-code-generation/); [SmartScope](https://smartscope.blog/en/ai-development/practices/rag-debate-agentic-search-code-exploration/); [Agentic search beats RAG for live codebases](https://ayushjj.github.io/knowledge-graph/insight/agentic-search-beats-rag-for-live-codebases)

### Inferences
- Arithmetic, not sourced benchmarks: 20,000 chunks × ~500 tokens = 10M tokens, which costs about $0.20 to embed once with text-embedding-3-small at $0.02/M. Storage at 1,536 float4 dims is about 6 KB per vector, or about 120 MB for 20k chunks; `halfvec` halves this. At 384 dims (BGE-small) it is about 1.5 KB per vector. Cost and storage are not the constraint at small-business scale; operational complexity and key availability are.
- Recommended staging for Airobot, given the "no extra infrastructure" rule:
  1. **v1 (no new extension, works with `postgres:16`):** `documents` (source, title, visibility, sync status, `deleted_at`) and `document_chunks` (document_id, workspace_id, ordinal, heading/page, content, `tsv tsvector GENERATED ALWAYS AS (setweight(to_tsvector('simple'|'english', title),'A') || setweight(to_tsvector(cfg, content),'B')) STORED`, GIN index, plus a btree on workspace_id). Query with `websearch_to_tsquery` + `ts_rank_cd`, add `pg_trgm` on document titles for typo tolerance, take the top ~20 chunks (the Anthropic finding), and let the bot's LLM pick or cite. Expose search as a bot tool (Claude-Projects-style "knowledge search"), and when an office's corpus is small (under ~200K tokens total, or a per-bot budget) skip retrieval and include it whole. `pg_trgm` ships with standard Postgres contrib; verify that it is present in the official image during implementation.
  2. **v2 (optional semantic):** switch the compose image to `pgvector/pgvector:pg16-*` (same official base plus the extension), add a nullable `embedding vector(n)` (or a separate table keyed by model name, since dims differ per model), and embed only when the office has an embeddings-capable key (OpenAI/OpenRouter) or local mode has Ollama. Fuse FTS and vector ranks with RRF (k = 60) in one SQL CTE. At tens of thousands of chunks per workspace with a `workspace_id` filter, start with exact scan (no HNSW) to avoid post-filter recall loss, and add HNSW plus `hnsw.iterative_scan` only if latency requires it. Leave a `TODO(air):` naming the tradeoff.
  3. **v3 (quality):** optional contextual-chunk headers (document title + section path prepended before indexing, a cheap non-LLM variant of contextual retrieval), and optional LLM rerank of the top 20–50 using the office's own model.
- BM25 extensions (`pg_search`, `pg_textsearch`) are not in the official or pgvector images and `pg_search` is AGPL, so they conflict with a simple self-hosted image. Built-in FTS is the pragmatic lexical choice at this scale.
- Language config matters for FTS stemming. A per-office language setting, or `simple` as a safe fallback for mixed languages, avoids English-only stemming.
- Re-embedding on model change rewrites every vector row. Storing `embedding_model` per row and re-embedding lazily avoids a big migration and the MVCC-bloat concern ClickHouse raises.

## 4. Text extraction for PDF, DOCX and HTML in a Rust server, and pitfalls

### Takeaway
Pure-Rust options exist and are adequate for born-digital documents: `pdf-extract` (on top of `lopdf`) for simple PDF text, the newer `pdf_oxide` for richer extraction, and `docx-lite` (zip + quick-xml) or a hand-rolled read of `word/document.xml` for DOCX. The hard cases are format-independent: scanned PDFs with no text layer need OCR, multi-column reading order, ligatures and Unicode normalization, and tables or repeated headers that pollute chunks. Enterprise products solve these with layout-aware or OCR parsers (e.g., Agentforce offers Docling or LLM-vision parsing).

### Cited Findings
- `pdf-extract` exposes `extract_text(path)` plus in-memory variants and is built on `lopdf` for parsing. — [pdf-extract docs.rs](https://docs.rs/pdf-extract/0.7.6/index.html); [pdf-extract README 0.7.9](https://docs.rs/crate/pdf-extract/0.7.9/source/README.md)
- `lopdf` is a low-level PDF manipulation library with no built-in extraction, though it ships an `extract_text` example. — [lopdf extract_text example](https://docs.rs/crate/lopdf/latest/source/examples/extract_text.rs); [pdf_oxide README (benchmark table)](https://docs.rs/crate/pdf_oxide/0.3.77/source/README.md)
- `pdf_oxide` offers `extract_text`, `extract_chars`, `extract_images` and Markdown conversion, and claims "5× faster than pdf_extract" (author's own benchmark). — [pdf_oxide README](https://docs.rs/crate/pdf_oxide/0.3.77/source/README.md)
- `docx-lite` depends only on zip, quick-xml and thiserror, with zero unsafe code. It supports paragraphs, tables and basic formatting via `extract_text(path)` and `parse_document_from_path`. 0.2.0 added footnotes/endnotes, and 0.1.0 listed lists and headers/footers as "coming soon". DIY DOCX extraction reads `word/document.xml` from the ZIP and collects text runs per paragraph. — [docx-lite 0.2.0](https://docs.rs/crate/docx-lite/latest); [docx-lite 0.1.0 README](https://docs.rs/crate/docx-lite/0.1.0/source/README.md); [orbok-extract docx.rs](https://docs.rs/orbok-extract/0.17.1/src/orbok_extract/docx.rs.html)
- `kreuzberg` is a Rust crate with an extraction module that includes DOCX handling (a broader document-extraction library). — [kreuzberg docx module](https://docs.rs/crate/kreuzberg/4.9.7/source/src/extraction/docx/mod.rs)
- Pitfalls: scanned or photographed PDFs are valid PDFs that yield empty text, so detect them and route them to OCR separately. Content streams come out in drawing order, so two-column layouts interleave lines. Some libraries' "reading order" is just a (y, x) sort, so test on a two-column document. The "fi" ligature can come out as U+FB01, and NFKC normalization fixes search/dedup. Tables flatten, multi-page tables lose headers, and repeated headers/footers end up in every chunk. — [DEV: hidden failure modes of PDF processing](https://dev.to/iterationlayer/the-hidden-failure-modes-of-pdf-processing-2kmh); [DEV: PDF parsing, why it's still hard](https://dev.to/multigrid/pdf-parsing-why-its-still-hard-3n8g); [Twig: PDF extraction issues](https://www.twig.so/dev/rag-scenarios-and-solutions/chunking/pdf-extraction); [DEV: PDFs break RAG pipelines](https://dev.to/katash/pdfs-break-rag-pipelines-5amf)
- Enterprise reference: Agentforce offers LLM-based multimodal parsing or Docling (layout analysis + OCR) and recommends loading CSV/JSON/XML as structured data rather than chunking it. — [Salesforce: Agentforce and RAG](https://www.salesforce.com/agentforce/agentforce-and-rag/)
- Product limits for comparison: HubSpot vaults accept PDF/MD/HTML/PPTX/TXT (UTF-8)/DOCX up to 50 MB, and Copilot Studio accepts Word/PowerPoint/PDF/Excel up to 512 MB. — [HubSpot knowledge vaults](https://knowledge.hubspot.com/ai/manage-breeze-context-with-knowledge-vaults?gad=1); [Copilot Studio unstructured data](https://learn.microsoft.com/en-us/microsoft-copilot-studio/knowledge-unstructured-data)

### Inferences
- For v1, support TXT/MD/HTML/CSV natively, DOCX via `docx-lite` or a small zip + quick-xml reader, and PDF via `pdf-extract` or `pdf_oxide`. Run extraction in `tokio::task::spawn_blocking` with a size cap and timeout, and catch panics (`std::panic::catch_unwind`) so a malformed file can't take down a request handler, in line with the "no unwrap in handlers" rule. That PDF crates panic on malformed input was not verified here and is a precaution.
- Detect "no text layer" (extracted chars per page near zero) and mark the document "needs OCR" in the UI instead of silently indexing nothing. This is one of the "bot ignores my file" root causes users can't see. OCR can be delegated to the user's own vision-capable model (send page images), or left as a TODO, since a bundled OCR engine would add heavy native dependencies.
- Normalize text (NFKC, collapse whitespace, strip repeated header/footer lines) before chunking. Chunk by headings/paragraphs into a few hundred tokens (Anthropic's guidance; Chroma's 200–400 token findings) and store page or heading for citations.
- For HTML/website ingestion, the same normalization applies. Prefer sitemaps over link crawling (the Chatbase tip) and respect URL-stem scoping (the Intercom pattern).

### Gaps
- `pdfium-render` (PDFium bindings), `docx-rs`, and Rust HTML-to-text crates (e.g., `html2text`, `scraper`) were not researched; no citable comparison was found.
- No source was found documenting panics or robustness issues in `pdf-extract`/`lopdf` on malformed PDFs; the advice above is precautionary.
- No Rust-native OCR option (e.g., Tesseract bindings or ONNX OCR) was evaluated.
