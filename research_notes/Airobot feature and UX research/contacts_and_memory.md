## Q1. Contacts/CRM: how agent products model contacts and let agents read and write them; the minimum useful model; linking; complaints; import

### Takeaway
Every product treats the contact (person) as the hub record, often with an optional company, and keeps a timeline of linked activity (emails, calls, meetings, notes, tickets, deals or orders). Email is the de facto identity key for matching and deduplication. The safest agent-write pattern is the one Attio uses: an agent can create records or *suggest* updates, and a human approves them. Users and consultants most often complain about duplicates and messy, overlapping fields, which make agents act on the wrong record or contact the same person twice. Small businesses mostly want something close to a spreadsheet.

### Cited Findings

**Complaints: duplicates, messy data, junk records**
- Consultancies report that duplicate contacts can make HubSpot's Prospecting Agent send outreach to both records, so one person gets two different emails. In another case, a Customer Agent answered from the wrong duplicate and found no order **[3rd-party]** — [Campaign Creators](https://www.campaigncreators.com/blog/breeze-agents-run-on-data-here-s-what-breaks-hubspot-ai); [InsideA](https://insidea.com/blog/ai/breeze-agents-go-live-portal-problems) (search summary; the summary did not say which example came from which post)
- Overlapping status fields (lifecycle stage, lead status, deal stage, customer status, qualification status) confuse agents. With messy or duplicated records, agents produce poor results "just faster and at a bigger scale" **[3rd-party]** — [HackerNoon](https://hackernoon.com/why-ai-agents-fail-in-messy-crms-a-four-layer-readiness-test-for-revenue-teams); [Insycle](https://www.insycle.com/prepare-crm-data-for-ai/) **[vendor]**. Vendors recommend deduplicating before connecting an agent, and having agents *flag* stale records instead of deleting them — [Cassidy AI](https://www.cassidyai.com/blog/ai-agents-for-data-hygiene) **[vendor]**; [Salesforce SMB blog](https://www.salesforce.com/blog/small-business/prepare-your-data-for-ai-crm/) **[vendor]**
- Independent reviews of Breeze Customer Agent are very thin: G2 had 2 reviews on the main Breeze page and 4 for Customer Agent. The recurring complaint is cost (it is priced at $0.50 per resolved conversation) and credits shared across agents **[3rd-party, competitor-written]** — [eesel.ai review](https://www.eesel.ai/blog/breezecustomer-agent); [G2 Breeze reviews](https://www.g2.com/products/hubspot-breeze/reviews)

### Inferences
- Minimum useful contact model for Airobot, drawn from the common denominator above: name, email(s), phone(s), optional company, tags, owner or bot, source (manual, Gmail, Google Contacts, Stripe, Shopify, CSV, bot), email-marketing consent as state, level and timestamp in Shopify's shape, `last_contacted_at` and `last_activity_at` roll-ups as HubSpot keeps them, `deleted_at`, and visibility, which AGENTS.md requires. Everything else can live in the existing app tables (leads, appointments, tickets, invoices) through a `contact_id` foreign key.
- Identity key: a normalized email, lowercased and trimmed, unique per workspace, with phone as the second key. This matches HubSpot's "block create on existing email", Folk's email/domain merge, and Shopify connectors' email-first upsert. Store external ids (`stripe_customer_id`, `shopify_customer_id`, Google resource name) on the contact or in a small `contact_identities` table so re-imports update records instead of duplicating them.
- Airobot bots already write records with `ADD <app-slug> {json}` lines (`src/office/context.rs`). Without a dedup-on-write step that runs before insert, this is exactly the "agent creates junk or duplicate records" failure. Follow Attio's model: a bot may create a contact only when no email or phone match exists. Edits to an existing contact become *suggestions* routed into Airobot's existing approvals.
- Timeline: one `contact_events` list (message, email, booking, invoice, ticket, note), each holding a reference to its source row. HubSpot shows the timeline is a view over linked activities rather than copied data.
- Consent must be stored as its own field with a timestamp, not as a tag. Bots should check it before any outbound marketing message. Shopify and Dotdigital show unsubscribes are expected to stick.

### Gaps
- Pipedrive AI: no primary documentation found on agent read/write, enrichment or dedup of contacts. One 2026 third-party comparison mentions only a ChatGPT integration (Dec 2025) and AI reports — [ZoomInfo comparison](https://pipeline.zoominfo.com/sales/pipedrive-vs-zoho).
- Clay, Lindy and Sintra contact models: not researched in depth within the tool budget.
- No Reddit, Hacker News or G2 threads were surfaced with first-hand user complaints about agents creating junk CRM records. The available evidence is consultancy and vendor blogs.
- No primary docs found for Google Contacts (People API) or Stripe customer import matching rules into a CRM.
- HubSpot's association-label model was not confirmed from primary docs.

## Q2. Sessions and memory: how ChatGPT, Claude, Copilot, Gemini, Lindy, Sintra, Relevance AI, Agentforce and Fin handle sessions, long-term, team and per-customer memory; what users like and dislike; what controls they ask for

### Takeaway
By late 2025 the major assistants had converged on the same set of features: (1) explicit "saved memories" or a memory summary the user can view and edit, (2) optional implicit recall from past chats, (3) project-scoped memory to separate clients, (4) an incognito or temporary chat that saves nothing, and (5) admin kill switches for teams. Business agent products add per-customer memory with retention windows (Fin: 45 and 180 days) and identity-keyed memory (Agentforce). Users complain most about memory bleeding across clients, memories silently dropped when storage is full, deleted memories coming back, and memory that is opaque or collected without being asked.

### Inferences
- Airobot needs at least four memory scopes, because users repeatedly ask to separate clients and work areas: **office** (shared business facts, brand voice, rules; the existing `workspace_lessons` table already covers rules), **bot/area** (procedure and style per area bot), **contact** (facts and recent-conversation summaries per customer, like Fin and Agentforce), and **thread/session** (rolling summary). Retrieval should never cross from one contact's memory into another contact's conversation. That is the "memory bleed" failure in ChatGPT.
- Fin's choice to hide memory from teammates is the opposite of what a small-business owner would want. In Airobot's single-owner office, a visible per-contact memory list is the natural place for it, and it doubles as the "notes" field of a CRM.
- Retention windows are a simple, defensible default: summaries expire after roughly 45 days and facts after roughly 180 days unless pinned, following Fin. This bounds growth and privacy exposure without a capacity cap that silently fails, which is the most common ChatGPT complaint.
- Deletion semantics confuse users when memory and source chat are decoupled (ChatGPT, Copilot, Gemini all say deleting one does not delete the other). Airobot should show the source link on each memory and offer "delete memory" and "delete conversation" as explicit, separate actions.

### Gaps
- Gemini Gems and Microsoft Copilot Pages (shared, persistent workspaces) were not researched in detail.
- No first-hand Reddit threads (r/ChatGPT, r/ClaudeAI, r/AI_Agents) were surfaced by the search tool. User opinion here comes mostly from the OpenAI Community forum, Simon Willison and blog commenters.
- No published user feedback specific to Claude's project memory or Fin Memory was found.
- The Lindy engineering post on its memory agent could not be read in full; see Q4 for the search summary.
- No information on Agentforce memory retention periods or user-facing deletion controls.

## Q3. UX patterns that make memory feel trustworthy

### Takeaway
Trust comes from making memory visible, editable, scoped and avoidable. Concretely: a readable memory list or summary, per-project or per-client walls, an incognito mode, admin off-switches, and honest feedback when a write fails. The two biggest trust breakers are memory created without being asked (96% of ChatGPT memories are model-initiated, per one study) and memory that leaks across contexts.

### Cited Findings
- **Visible, editable list or summary**: Claude keeps memories in one summary users can view and edit — [Claude blog](https://claude.com/blog/memory). Gemini added a bullet-point Memory summary with corrections after critics called Personal Context a black box — [TechRepublic](https://www.techrepublic.com/article/news-google-gemini-memory-summary-controls/); [VentureBeat](https://venturebeat.com/ai/google-adds-limited-chat-personalization-to-gemini-trails-anthropic-and-openai-in-memory-features). Copilot provides per-item delete and "Delete all" — [Microsoft Support](https://support.microsoft.com/en-US/Microsoft-365-Copilot/manage-copilot-memory-in-microsoft-365-copilot). Lindy stores memory as viewable and editable versioned files — [Lindy docs](https://www.lindy.ai/docs/teammate/memory)
- **Scoped memory**: Claude keeps a separate memory per project "to keep unrelated and confidential work separate" — [Claude blog](https://claude.com/blog/memory). ChatGPT has Project-only memory — [TechRadar](https://www.techradar.com/ai-platforms-assistants/chatgpt/chatgpt-project-only-memory-is-live-and-it-might-change-how-you-work-with-ai). - **Opt-out modes**: Claude incognito chats are "not saved to memory" — [Claude blog](https://claude.com/blog/memory). ## Q4. Published guidance on implementing agent memory and session summaries simply

### Takeaway
The current guidance converges on simple designs: a rolling summary of the conversation (compaction) plus a small set of structured notes outside the context window, keyed by scope (user, team, entity). Several practitioners have dropped vector databases for plain files or rows. Anthropic's advice is "do the simplest thing that works", and Lindy replaced RAG with a file system. An extraction step that decides ADD / UPDATE / DELETE / NOOP per fact (Mem0) or invalidates old facts with timestamps (Zep) handles contradictions.

### Cited Findings
- Anthropic (Sept 29, 2025, read in full) recommends three techniques. **Compaction** summarizes the context and restarts with the summary; Claude Code keeps "architectural decisions, unresolved bugs, and implementation details" and drops redundant tool output, and compaction prompts should be tuned to "start by maximizing recall" and then trimmed. **Structured note-taking** has the agent "regularly write notes persisted to memory outside of the context window" (to-do lists, a NOTES.md). **Just-in-time retrieval** keeps "lightweight identifiers" and loads data with tools. Overall advice: "do the simplest thing that works" — [Anthropic Engineering: Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Anthropic's memory tool is client-side: Claude reads and writes files in a `/memories` directory through handlers the developer implements, and the backend can be swapped for a database. Combined with context editing, it improved an agentic-search eval by 39% over baseline, versus 29% for context editing alone. Context editing cut tokens by 84% in a 100-turn eval **[vendor]** — [Anthropic: Context management](https://www.anthropic.com/news/context-management); [Claude docs: Memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool) (search summary)
- LangGraph: short-term memory is thread-scoped. Long-term memory lives in a store under custom namespaces (for example per user) and can be recalled from any thread. Memory types are semantic (facts), episodic (past experiences, often implemented as few-shot examples) and procedural (rules, often implemented by the agent updating its own prompt) — [LangChain docs: Memory concepts](https://docs.langchain.com/oss/python/concepts/memory); [LangGraph memory](https://docs.langchain.com/oss/python/langgraph/memory) (search summary)
- OpenAI Agents SDK has built-in Sessions that persist conversation history across runs. The cookbook shows a `TrimmingSession` that keeps the last N user turns and a summarizing variant. A personalization cookbook re-injects session-scoped memory notes into the system prompt after trimming — [OpenAI Agents SDK: Sessions](https://openai.github.io/openai-agents-python/sessions/); [OpenAI Cookbook: session memory](https://developers.openai.com/cookbook/examples/agents_sdk/session_memory); [OpenAI Cookbook: context personalization](https://developers.openai.com/cookbook/examples/agents_sdk/context_personalization) (search summary; compression code not seen). A community guide suggests trimming first and treating summarization as best-effort so a failure never blocks trimming — [aalok05 blog, Mar 2026](https://aalok05.github.io/ai/2026/03/12/agentic-session-management.html) **[3rd-party]**
- Lindy engineering replaced its RAG stack with plain files. A memory agent rebuilds them every 12 hours from Slack, Gmail, meetings and Lindy tasks, with separate files per user and per team, and a deterministic verifier checks the files still fit the context window **[vendor]** — [Lindy engineering: memory agent](https://www.lindy.ai/engineering/memory-agent) (search summary)
- Letta (MemGPT) uses three tiers. Core memory blocks always sit in the prompt and the agent can edit them. Recall memory holds the conversation history, with older messages compacted into a recursive summary. Archival memory is an indexed store queried by tools. "Sleep-time" agents review history every few turns in the background and rewrite the shared blocks — [Letta docs: agent memory & architecture](https://docs.letta.com/guides/agents/architectures/memgpt); [Letta blog: agent memory](https://www.letta.com/blog/agent-memory) (search summary)
- Mem0 (arXiv 2504.19413, Apr 2025) is a two-phase pipeline. Extraction pulls candidate facts. An update step retrieves similar existing memories and has the LLM choose ADD, UPDATE, DELETE or NOOP via tool calls — [arXiv 2504.19413](https://www.arxiv.org/pdf/2504.19413). A secondary source says Mem0 v3 dropped the LLM update/delete phase for ADD-only extraction, keeping manual delete — [Level Up Coding](https://levelup.gitconnected.com/choosing-an-ai-agent-memory-layer-lessons-from-mem0s-evolution-from-fde-pov-8b1268fa8735) **[3rd-party, unconfirmed]**. A 2026 study reports about 25% malformed JSON from one model configuration in extraction, plus misrouted contradictions — [arXiv 2606.15903](https://arxiv.org/pdf/2606.15903) (search summary; which paper reported this was not confirmed)
- Zep/Graphiti (arXiv 2501.13956, Jan 2025): facts are graph edges with `valid_at`, `invalid_at` and `created_at`. A contradicted fact is invalidated with a timestamp rather than deleted, which allows point-in-time queries. Search combines semantic and BM25 results with reciprocal-rank fusion — [arXiv 2501.13956](https://arxiv.org/html/2501.13956); [graphiti-core on PyPI](https://pypi.org/project/graphiti-core/0.8.7/)
- Salesforce's production split is one episodic summary per conversation plus semantic facts per person, extracted periodically during the session — [Salesforce docs](https://developer.salesforce.com/docs/data/agentic-memory-context/guide/agentic-memory-about.html) (search summary)

### Inferences
- A Postgres-only design that matches the guidance and AGENTS.md (no vector DB, cache or queue):
  1. **Thread rolling summary**: after every N messages, or when the token budget is exceeded, the bot rewrites one `summary` text column on the thread from the previous summary plus the new messages (Letta recursive summary, Anthropic compaction). The prompt gets the summary plus the last K messages (OpenAI TrimmingSession). This also gives a "resume where I left off" card.
  2. **Entity memory keyed by contact**: an `ADD`, `UPDATE` or `NOOP` decision per extracted fact (Mem0), stored as rows with `contact_id`, `source_message_id`, `valid_from` and `invalidated_at` (Zep-style invalidation instead of hard delete, which also satisfies the soft-delete rule). Also keep one episodic summary per closed conversation linked to the contact (Agentforce).
  3. **Office and bot notes**: short, always-in-prompt blocks (Letta core memory and Anthropic NOTES.md), editable by the owner. `workspace_lessons` already plays this role for rules.
  4. **Retrieval**: Postgres full-text search plus a recency filter on the contact's rows is likely enough at about a million requests a month. Embeddings can wait; per Anthropic's guidance, start simple. Leave a `TODO(air):` naming the tradeoff.
  5. **Background consolidation**: Airobot's existing dispatcher could periodically merge duplicate facts and expire old summaries (Lindy's 12-hour rebuild, Letta sleep-time). This addresses the "repeated semantic duplication" complaint from ChatGPT users.
- Validate extraction output strictly, and drop rather than store malformed JSON. The 2026 study's 25% malformed-output finding suggests this cannot be skipped.
